# LLMオンボーディングサマリー

新任エージェントが最初に読む資料です。ここは**入口**であり、一次資料ではありません。
数値・仕様・判断の根拠は必ず §3 の一次資料に当たってください。

最終更新: 2026-08-17

---

## 1. プロジェクト概要と目的

- **プロジェクト名称・領域:** headcoupled-3d-display / ヘッドカップルド3Dディスプレイ（fish-tank VR）。実時間顔追跡と非対称視錐台による裸眼立体表示。
- **最終成果物:** USBカメラで観察者の眼位置を実測し、通常の2Dディスプレイを「窓」として振る舞わせるアプリケーション。ブラウザ（WebGL2）が表示面、Python 3.13 のFastAPIサーバーが制御面、Python 3.10 / CUDA の別プロセスが顔認識を担う。
- **ビジネス背景・価値:** 出発点はChatGPTが生成した配布ZIP。**そのままでは動作しなかった**（WebSocket実装の欠落、Chromiumパス決め打ち、CLI発見失敗など）ものを、この機体で実際に動く状態へ持ち込み、かつ「どこまで実測で裏が取れているか」を検証可能な形で残すことが主目的。実装より**証跡の質**に価値がある。
- **現時点の進捗サマリ:** 実カメラでの表示は動作。作業計画書のDoD 14件中 **11件達成 / 3件未達**（DoD-6・DoD-7・DoD-9）。未達は閾値を緩めず未達のまま記録している。実カメラでのmotion-to-photon遅延は**未受け入れ**。

## 2. クリティカルな要求・制約

> 「壊してはいけない」ライン。逸脱する場合は必ず利用者の判断を仰ぐこと。

- **未測定を合格として扱わない。** 閾値を緩めて通すこと、測っていない条件を「たぶん大丈夫」で埋めることは禁止。未達は未達として記録する（DoD-6/7/9 が現にそうなっている）。
- **合成入力の成功は実入力の成功の代用にならない。** 合成データの生成側と描画側が同じ誤った規約を共有していればテストは通る。実際にこれが原因で、うさぎの向きが反転したまま全テストが通った実績がある。
- **生体情報をリポジトリへ入れない。** 個人用顔モデル `shape.pcd`、録画、撮影フレームはすべて追跡対象外。録画のファイル名・パスも記載しない（`$HEADCOUPLED_RECORDING` で受ける）。`temp/` と `artifacts/` は `.gitignore` 対象。
- **参照リポジトリを書き換えない。** `../facemesh_tracking` と `../apriltag-camera-calibrator` は読み取り専用。dirtyな作業状態をそのまま保つこと。
- **制御レーンの遅延を他の用途で犠牲にしない。** 姿勢の配信経路に同期処理を挟まない。過去にメッシュ配信をキャプチャループ内で同期POSTし、認識レートを1/3に落とした事例がある。
- **カメラは利用者が操作する。** カメラ・サーバーの起動は明示的な許可を得てから。作業終了時はプロセス、port 8000、`/dev/video0` を必ず解放する（DoD-14）。
- **CUDAのCPUフォールバックを成功扱いしない。** `providers_for("cuda")` はCPUを含むリストを返すため、実セッションの `get_providers()` を検査して先頭がCUDAでなければ非ゼロ終了する。
- **座標規約を変えない。** ディスプレイ座標系は「原点＝表示領域中心、+X＝観察者の右、+Y＝上、+Z＝観察者側、画面は z=0」。頭部の回転は視錐台を回さない（窓は物理画面に固定される）。

## 4. タスク境界（任せること / 任せないこと）

### 任せるタスク
- コードの実装・リファクタ・テスト追加、および**その検証の実行**
- 性能・精度の測定と、結果の記録（達成・未達を問わず事実として書く）
- ドキュメントの更新（陳腐化した記述の訂正を含む）
- 原因調査。ただし**コードだけで確定できることは確定させ、実測が要ることは実測する**
- サーバー・カメラの起動と停止（利用者の許可がある場合）

### 任せないタスク
- **閾値の緩和、DoDの判定基準の解釈変更。** 未達を達成に変える判断は利用者のもの
- **参照リポジトリ（`../facemesh_tracking` 等）の変更**
- **git履歴の書き換え**（`filter-repo` 等の破壊的操作）
- **リモートへのpush、外部への公開**
- **生体情報・録画のリポジトリ追加**
- 表示幾何の規約変更（座標系の符号、視錐台の構成、アンカー位置の意味）

## 5. インタラクション方針

- **回答スタイル:** 日本語。見出しと箇条書き・表を使い、結論を先に置く。コード識別子は原語のまま。
- **回答手順:** 事実 → 根拠（実測値・ファイル:行番号） → 判断 → 未確定事項。**推測と実測を必ず区別して書く**。
- **禁止事項・注意:**
  - 測っていないことを測ったように書かない。「〜のはず」で結論しない
  - 自分の誤りは短く訂正して次へ進む。過剰な自己批判・反省の反復は不要
  - 他エージェントの報告を鵜呑みにしない。数値は自分で再現して確認する
  - 「テストが通った」は「正しい」ではない。何を守るテストかを確認する
- **秘匿情報の扱い:** 顔モデル・録画・撮影画像は生体情報として扱い、パスも含めてリポジトリに残さない。`temp/` 配下は個人情報を含みうるためコミットしない。

## 6. 試行タスク（オンボーディング演習）

1. **座標規約の確認**: 観察者が自分の左へ10 cm動いたとき、画面を貫通して置かれた点群の「手前側」と「奥側」が画面上でそれぞれどちらへ動くか、`headcoupled_display.geometry.project_display_point` を使って数値で示す。符号の向きを説明できること。
2. **CUDAフォールバック検査**: `CUDA_VISIBLE_DEVICES="" just facemesh-ipc` 相当を実行し、**非ゼロ終了する**ことを確認する。CPUへ暗黙にフォールバックして動き続けないことが要点。
3. **未達DoDの読解**: `docs/performance_results.md` から DoD-6 が未達である理由を読み取り、「精度と遅延を同時に満たす `--detector-refresh-interval` が存在しない」構造的な理由を自分の言葉で説明する。

## 7. 運用ルール・変更管理

- **ドキュメント更新時の記載ルール:** 事実が変わったら訂正し、**訂正した旨と日付を残す**。過去の測定値は書き換えず、測定時の条件を追記する（点数が変わったのに数値だけ差し替えると「新条件で測った」という嘘になる）。
- **TBDの扱い:** 未確定・未測定は空欄にせず「未検証」「未達」と明記し、何を測れば確定するかを併記する。
- **レビュー/承認フロー:** commitは意味単位に分ける。性能閾値が未達のまま実装した場合、**commit件名に成功表現を使わない**（`perf:` ではなく `feat:` にする等）。
- **その他の運用ルール:**
  - 作業終了時にサーバー・producer・port 8000・`/dev/video0` を解放する
  - `just check` と `ruff format --check` を通してからcommitする
  - 並行エージェントと同じファイルを編集しない。担当を分けてから着手する

### 付録: 参考情報

**主要リポジトリ/ディレクトリ**

| パス | 役割 |
|---|---|
| `src/headcoupled_display/` | 制御面（FastAPI、幾何、姿勢推定、プロファイル） |
| `src/headcoupled_display/static/` | 表示面（WebGL2レンダラ、ダッシュボード） |
| `scripts/facemesh_ipc_producer.py` | 認識プロセス。**Python 3.10 / CUDA 環境で動かす** |
| `components/facemesh_tracking/` | 同梱の顔追跡スナップショット（3次元復元機能を含まない版） |
| `../facemesh_tracking` | 顔認識の本体。**読み取り専用** |
| `../apriltag-camera-calibrator` | カメラ内部パラメータ較正。**読み取り専用** |

**代表的なコマンド**

```bash
just setup                 # 制御側環境（Python 3.13）
just setup-facemesh        # 認識側環境（Python 3.10 / CUDA）
just check                 # ruff + unit（e2e と recorded_cuda は除外）
just test-e2e              # ブラウザE2E（Chromium起動）

# 実カメラ表示（2プロセス。serve-ipc を先に起動する）
just serve-ipc <shape.pcd> <calibration.json>
just facemesh-ipc

export HEADCOUPLED_RECORDING=/path/to/recording.avi   # 録画を使う測定
just benchmark-recorded && just summarize-performance

# プロファイルの確認。設定値ではなく最終的な4x4変換行列から逆算した値を表示する
just profile-summary config/hardware_profile.local.json

# 録画再生。4つの入力は「同じ撮影セッションのもの」でなければ意味がない
#   録画 / その保存済みlandmarks / 個人の顔モデル / そのカメラのK,D
just replay-recording <landmarks.json> <recording.avi> <shape.pcd> <calibration.json>

# tagcalの較正結果をハードウェアプロファイルへ取り込む（内部パラメータのみ。
# カメラ・ディスプレイ外部姿勢は別物なので上書きされない）
just import-tagcal <calibration.json>
```

**プロファイルは3種類に分かれている。出自が違うので混ぜないこと。**

| ファイル | 内容 | 出自 |
|---|---|---|
| `config/hardware_profile.demo.json` | 動作確認用の人工値 | `synthetic_demo_not_measured` |
| `config/hardware_profile.local.json` | この機体の設置値（上15.0 cm / 俯角12.0°） | `user_confirmed_mount_synthetic_intrinsics`。**目視確認であり実測ではない** |
| `config/scene_profile.default.json` | 何をどこにどの大きさで描くか | 較正結果ではなく**表示上の選択** |

シーンは「点群のAABB中心を原点に置き、最長辺が0.24 mになるよう等方スケール」する。
レンダラーは配置定数を持たず、読み込み時に `T(anchor) · S · T(-aabb_center)` を一度だけ組む。
この設定で点群は画面平面を貫通するため、**前面（頭と逆に動く）と背面（頭に追従する）で
逆向きの視差が同時に観察できる**。これが幾何が正しいことの目視確認点になる。

**依存ライブラリ**

- 制御側: FastAPI / Uvicorn / websockets / NumPy / SciPy / OpenCV / Pydantic / Typer / pytest / Playwright
- 認識側: onnxruntime-gpu 1.18.0（**CUDA 11.8 / GTX 1070 の組み合わせに依存**。cuDNN 9 ではConvが動かない）
- 表示側: 外部依存なし（WebGL2を直接使用。CDN読み込みもなし）

**環境変数**

| 変数 | 用途 |
|---|---|
| `HEADCOUPLED_RECORDING` | 録画のパス。リポジトリには記載しない |
| `HEADCOUPLED_PROFILE` / `HEADCOUPLED_SCENE` / `HEADCOUPLED_USER_PROFILE` | 各プロファイルの既定パス上書き |
| `HEADCOUPLED_CHROMIUM` | E2Eで使うChromium |
| `HEADCOUPLED_FORCE_SOFTWARE_GL` | ソフトウェアGLを強制（**性能測定には使わない**。SwiftShaderでは約1.8 fpsしか出ない） |
